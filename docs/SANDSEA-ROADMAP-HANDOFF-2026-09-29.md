## 3. 建议的后续版本顺序

原则：一次只认领一两个相邻工作；继续维护单文件、零依赖、老存档兼容和可自动验证。以下是建议而非已批准实现范围；每个实际编码切片仍需在 Issue #11 报号。

   - 边界：只做渲染；不改 C 键、`foeStrike()`、快捷栏行为、生成/存档。

### P1 — 沙步 v1.1：补齐自动化边界并点测手感

PR #42 的首版已合并。先做短的硬化验证，而不是马上加另一套技能成长：

- 增加用例：墙/窄道被阻挡时位移不会穿模；没有安全落点时不移动、不启动冷却/闪避；空中、骑乘、钩爪牵引、水中、岩浆中、离地时拒绝触发；输入方向（WASD 与静止朝向）符合说明。
- 检查 C 事件只响应一次按下（不因键盘重复触发），冷却期间没有重复位移；验证暂停/帮助面板打开时不触发。
- 当前自动测试验证的是可走位置的位移和 `foeStrike()` 边界，**没有**用一个刻意挡路的实体墙断言“不会穿墙”；虽然逐段调用 `aabbFits()`，这仍值得单独回归。
- 桌面实际点测：正常帧率下闪避窗口是否容易理解/掌握；高延迟或低帧率时窗口与提示是否仍可感知。不要把头less 时间推进测试误写成真实玩家手感验证。
- 不要在这一轮同时加 `combatMastery`、新存档字段、敌人 AI 或近战反击。若想做这类扩展，先单独写规格并评估平衡。

### P2 — 战斗可读性：敌人攻击预警，与沙步形成玩法组合

等渲染和生成修复车道稳定后，再选**一种**敌人族群做垂直切片：

- 近战敌人在攻击前给短暂、可识别的准备动作/声音/视觉提示；远程单位先只考虑清晰的蓄力提示，不同时重做所有 AI。
- 保持现有 `foeStrike()` 作为近战敌方伤害的统一入口，使沙步闪避规则有稳定边界；攻击范围、取消条件和提示窗口要由测试明确。
- 验收：预警时不提前扣血；攻击动作/攻击者实际伤害一致；离开有效距离或攻击者被打断时不会产生幽灵命中；窗口内沙步可躲、窗外仍正常受伤；非敌方直接伤害仍然独立。
- 先做一个代表性敌人，经显示态截图和玩法点测后再推广；不要一次性翻修全体怪物。

### P3 — 中后期成长：先盘点现有货币与奖励，再做一个有上限的资源出口

游戏已有核心货币、装备耐久/附魔、主线、悬赏、编年史、声望、地标纪念品、试炼与宝库。下一步应减少“一次领取后无后续目标”的感觉，而不是再堆一个无关子系统。

- 候选方向：复用祭坛，为现有武器/战斗提供少量有上限的阶段性升级；或为已完成的试炼/悬赏增加周期性、可选的高难度目标。先选一个方向做设计稿和资源消耗模拟。
- 规格需写清楚：奖励来源、花费、最大等级、是否可重置、与现有附魔/耐久/等级倍率的叠加上限、对新档与旧档的默认值。
- 若添加存档字段，须提供缺字段旧档兼容、错误类型/越界值校验、保存/载入往返测试；避免免费重复领取或无限堆叠造成数值膨胀。
- `combatMastery` 目前只是讨论过的名字，不能假设它已经存在或预先写入存档。

### P4 — 发布前稳定性轮

在两项左右的玩法/画面增量合入之后再统一做，不需要每次重做整套大型测量：

- 以固定种子回归生成、建筑/门口、间歇泉、载具和新增战斗内容；保留至少一个老存档缺字段矩阵。
- 跑 `node tools/headless.mjs selftest`，另用 `shot`/浏览器检查桌面菜单、战斗 HUD、重点新内容；记录 SwiftShader/无头的限制。
- 对低/中/高/极致画质做帧率与主要内存趋势抽查，避免每帧分配、未限量粒子、shader 过度分支。
- 手机端此前是明确未承诺的范围。若未来要支持，应单独验证触屏输入布局/性能，并先让用户确认扩大范围；不要将桌面无头截图当作移动端验证。
