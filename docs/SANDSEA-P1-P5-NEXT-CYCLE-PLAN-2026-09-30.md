## 1. 阶段总览：从 P1 到 P5

### P1｜优化与平衡：先验证已经做出的战斗

**核心目标：**避免新战斗效果拖慢渲染、堆积粒子或造成“看见预警却仍被判命中”的误判。先测量与真人点测，再只按证据调整参数；本阶段不新增敌人招式。

**已知基线（代码事实，不等于性能结果）：**圣甲虫预警 `0.52 s`、冲锋 `0.38 s`、收招 `0.58 s`；触发距离上限 `8.5`、水平命中半径 `1.55`、冲锋伤害 `2`。反击窗口 `2.0 s`，加成率 `0.35`、封顶 `+3`。粒子硬上限由渲染距离决定：`RENDER <= 6` 时 90、`<= 8` 时 220、其余 420；触屏入口把渲染距离限制到最多 4 并将粒子缩放设为 0.4。单只圣甲虫一次预警约每 0.14 秒发一批 8 颗粒子；这些数字须在开工时再核对最新代码。

**实施步骤：**

1. PR #51 已合并；先从 Issue #11 确认没有并行敌人 AI 改动，按 A1–A7 清单取得用户/测试者对预警、冲锋与反击时机的具体体验反馈。若无法真机点测，明确保留，不伪造结论。
2. 固定对照环境：浏览器版本、操作系统、设备/GPU、世界种子、画质档、视口尺寸、是否触屏。先测基线版本和候选版本；SwiftShader 只做自动回归/渲染冒烟，不能当作真实 GPU 帧率基准。
3. 建立可重复场景：无战斗基线；1 只圣甲虫循环；3 只错峰预警；在生成上限允许时的高压同屏遭遇。每种画质低/中/高在同一设备、同一种子、同一镜头下运行。每次预热 10 秒、记录 30 秒、重复 3 次；记录 RAF 帧时 p50/p95、`window.__game.fps`、每次预警/粒子峰值、自动降画质次数与是否出现视觉掉帧。
4. 若现有观测接口不足，只增加只读、非存档诊断值（例如粒子数/上限、圣甲虫各状态计数），不得引入每帧 DOM 文本更新。诊断指标属于开发验证，不改变玩家存档或玩法 API。
5. 功能回归逐项验证：`idle → telegraph → lunge → recover`；预警阶段不伤害；锁定方向后侧移躲避；受击、视线丢失、离开射程/方向时取消；冲锋最多一次命中；只有被沙步避开的标记攻击授予反击；错误目标不消费、正确目标仅消费一次、超时/离场失效；环境伤害边界保持不变。
6. 对比 1280×720 桌面、844×390 横屏触控和必要时的窄屏；确认暖金实体/粒子在亮/暗背景可辨、触屏按钮不遮挡任务卡或教程卡，低画质下反馈不消失。
7. 只有出现可复现问题才调一个变量（预警时长、射程、命中半径、粒子频率或加成率），每次变化都给出 before/after 测量与针对性测试；不要一次同时调多个参数。

**建议验收门槛（P1 开工时与用户确认参考设备）：**同设备、同浏览器/GPU、同种子/画质/视角的**相同战斗场景**中，候选版本 p95 帧时较参考版本的可比基线恶化不超过 10%；选定低端参考设备在 3 只错峰战斗下无持续 5 秒以上低于 30 FPS；粒子数始终不超过当前 cap 且多个循环后回落；命中只发生在预警/冲锋可理解范围内。没有相应真机时只能报告“未测”，不能标记性能验收通过。

**任务拆解（建议一个 PR）：**

| P1-C 确定性压力/边界测试 | selftest 或临时 CDP 脚本 | 多状态循环、取消/命中边界、粒子 cap/回收、存档 schema 全覆盖 |
| P1-D 参数点测 | 仅必要的一个参数修订及 before/after 表 | 真人点测能躲且看得懂；自动测试不靠放宽条件通过 |

### P2｜丰富战斗选择：增加一种不同的读招与反制

**核心目标：**令玩家根据敌人种类作不同选择，而不是把所有敌人统一成追逐/闪避。

**步骤：**
1. 先盘点敌人 AI 与 Issue #11 现有认领，确认没有重复的弓手蓄力、重击前摇或其他攻击切片。
2. 只选一种与圣甲虫节奏明显不同的敌人；候选如远程蓄力（先找掩体/移动）或重型近战（侧闪/精准反击）。按现有敌人、动画、移动端表现和实现风险打分后再定，不先改多个种类。
3. 写出状态机、预警颜色/形状、攻击轨迹、有效躲避方向、命中区、取消条件、冷却、受击反馈、是否授予反击。预警必须在攻击前且能被其他背景辨认。
4. 将敌击接入既有统一伤害入口；确认 `sandStep` 的规避边界与环境伤害不被破坏。状态默认不持久化。
5. 覆盖正常预警/命中、视线/距离/受击取消、目标离场、重入/重复命中、躲避方向边界、普通与特殊攻击资格。
6. 桌面/横屏截图与至少一轮真人节奏点测后单独开 PR。

**验收：**一次仅新增一种敌人行为；确定性测试覆盖成功/失败/取消；移动端读招有足够对比；既有敌人和环境伤害回归全绿。

### P3｜深化装备与成长：建立有限的资源花费闭环

**核心目标：**让战斗与探险所得有持续用途，同时避免无限伤害叠加或免费刷取。

**步骤：**
1. 对现有能量核心、祭坛、耐久/修理、附魔、声望、悬赏和试炼奖励做资源来源/去向表；先发现闲置资源或过强升级点。
2. 比较 2–3 个方案（例如一件武器的有限专精、现有祭坛的强化分支、耐久修理的战斗代价），按理解成本、复用程度、存档影响、重复刷取风险评分。
3. 选择一个资源闭环，明确来源、单次消耗、升级上限、收益曲线、重置规则与 UI 告知。优先复用现有资源，不加新货币。
4. 写经济模拟表：最短/最长获得路线、最大可叠加伤害、重复领取及退出/载入期间套利；为每项设硬上限和服务端/客户端唯一判定入口（本游戏为本地单机，重点是逻辑幂等）。
5. 若必须新增存档字段，按“字段缺失、旧版本、空值、负数、过大/NaN、保存—载入往返、死亡/新世界重置”构建兼容矩阵；否则保持 schema 不变。
6. 加 UI 截图和确定性购买/消耗/上限测试，更新教程/变更说明后单独 PR。

**验收：**来源与花费能闭合；至少一个明确上限；无重复免费领/无限叠加；现有配方、耐久、修理和旧档回归通过。

### P4｜扩展可重复关卡：古文明微型遗迹/试炼

**核心目标：**将战斗节奏和成长奖励放在一段有入口、目标、结尾的可重玩探险里，而不是再加孤立事件。

**步骤：**
1. 盘点金字塔、遗迹、地标、任务、Boss、机关与奖励的现有生成/存档入口；选择最少改动的复用方案。
2. 设计一条入口明确的微型路线：2–3 个目标节点（探索/机关/战斗组合），一个精英或 Boss 机制，一个明示的有限奖励出口。
3. 先做纸面地图与每个节点的成功/失败/绕过路径；保证玩家不会因为方块覆盖、实体阻挡、退出/重载或生成高度变化软锁。
4. 结构放置必须 seed-deterministic，并避免覆盖既有建筑、地标、重要方块或生成边界；需要标记时先在 Issue #11 协调新编号。
5. 设计可重复挑战规则：入口重置、清场判定、奖励上限/冷却/首次与重复奖励差异；若需要持久化通关状态，写明旧档默认行为。
6. 自动跑固定种子 `424242` 与至少两个额外种子；检查结构连通性、节点可达、战斗胜利、死亡/退出/重进及奖励幂等；拍桌面/窄屏图。

**验收：**不同种子无结构覆盖和软锁；提示能让玩家看懂下一目标；路线可结束和重玩；奖励有限且不被退出/重载重复领取。

### P5｜发布前稳定化：全系统验证与风险收口

**核心目标：**合并/发布前对新增切片和历史系统做一致的兼容、性能、布局和文档验收。

**步骤：**
1. 固定发布候选 commit，冻结非阻断功能需求；列出所有合并 PR、变更文件、保存字段、快捷键、方块/配方与已知风险。
2. 回归默认、`424242` 与额外固定种子；完整 selftest 全绿。每个新增保存字段再跑旧档缺失/坏值/往返矩阵。
3. 跑战斗主链、关卡进出、死亡/重生、新世界、暂停/载入、奖励领取/重置的端到端路径。
4. 低/中/高（极致可选）画质；桌面 1280×720、横屏触控 844×390、竖屏旋转提示；记录 WebGL renderer。真机帧率与真实输入单独报，不能被无头结果代替。
5. 检查浏览器错误、输入/状态残留、粒子和实体上限、存档兼容、变更日志、路线图和 Issue #11 交接；关闭或标明所有未解决风险。
6. 每个主题维持独立 PR；最后由用户决定合并和发布。

**验收：**全量自动化通过；没有已知发布阻断；实际未覆盖项明示；旧档可用；所有 PR/文档状态相互一致；用户确认发布边界。
